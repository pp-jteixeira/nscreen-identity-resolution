# PII Clean project instructions

## Purpose and history

Understand evidence for email–NPI attribution before choosing scores. Use a dbt-style structure while keeping the project's scope iterative and understandable.

Use all currently retained source history, not the latest partition. Preserve older attributions when later records report another NPI. Repeated snapshots are not independent confirmations. Unknown dates stay unknown.

Vendors: HealthLink, QuantumMedica, Medscape, Endato, RocketReach, DRDB and Haymarket. See the [source map](docs/00_source_map.md) for exact tables and columns.

## Layer boundaries

**Staging:** stage each vendor input table separately. Keep every row and original column, with cleaned/type-converted helper fields. No filters, joins, unnesting, deduplication, aggregation or latest-day selection. Keep malformed values and missing keys visible.

**Intermediate:** keep vendors separate. Perform necessary unnesting and source-table joins; attach NPI-reference, claims/facility and cookie-location evidence when reviewed. Build source-specific and common metrics here. Preserve unmatched or missing-evidence records so coverage can be measured. Each vendor has one intermediate SQL file with named CTEs; the only other intermediate models are the shared NPI-name and nickname-variant lookups. Preserve raw vendor fields in record_payload. Combine rows only when all raw columns except day agree, before unfolding emails. Metric models select nonempty email/NPI keys and preserve one row per exact source record and email position, keyed by source/metric_row_id. Defer email–NPI deduplication until after metrics and indicators.

**Final:** publish `iceberg.jteixeira_ipa.pii_clean` as an Iceberg table combining the seven reviewed intermediate metric views with `UNION ALL`. The final model only unions complete vendor outputs; all metric calculations remain in intermediate. Validate identical column names, order and types before publication. Preserve source/metric_row_id grain, historical observations and nullable outcomes. Individual attribution scoring, confidence scoring, weights and cross-vendor corroboration/contradiction scoring remain deferred. Descriptive state-agreement indicators are implemented and do not assign scores.

## Iterative metrics

Review each metric's definition and assumptions before implementation. For each metric:

1. Agree its question, inputs, calculation and edge cases.
2. Implement and validate it in intermediate.
3. Measure every vendor separately: availability, missingness, distributions and affected counts.
4. Review its explanation, examples and statistics before advancing.

Count and name denominators. Pair counts with percentages when meaningful. Distinguish raw rows, emails and links. Keep unknown, not applicable, not measured and zero separate; label approximations. Do not infer scoring weights from coverage alone.
